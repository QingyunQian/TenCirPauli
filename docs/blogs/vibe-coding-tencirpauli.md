# 如果不逐行审阅 AI 写的代码，会发生什么？

## ——TenCirPauli 的一次极端 Vibe Coding 实验

在[上一篇文章](why-i-developed-tencirpauli.md)中，我解释了为什么要开发 TenCirPauli。TensorCircuit-NG 很适合规则的张量计算、自动微分和加速器执行。量子算符处理和线路分析中的许多结构化任务，则需要动态数据、离散计算和变长结果。为这些工作提供一个 Rust-native 运行时，是 TenCirPauli 最初的动机。

这篇文章谈开发方式。我在 TenCirPauli 上做了一个极端实验：实现代码交给 AI，自己不逐行审查，看看 Spec、AI Review、自动化测试和 Benchmark 能不能支撑一个严谨的科研软件项目。

## TensorCircuit 为什么要保持“半古法”

在 TensorCircuit 的长期开发中，我一直采用比较保守的工作方式。遇到 issue 或 feature，我会先想清楚实现方案，再把具体要求告诉 AI。AI 修改之后，我会检查每个文件、每处增改，很多时候逐行确认代码是否符合项目的风格和规范。

这套方式让 TensorCircuit 保持了很好的稳定性。它保护既有的抽象、语义和代码风格，也能及时拦住 AI 为了完成任务而引入的局部方案。在 AI 生成能力快速提升的今天，逐项人工审阅是一道稳定器：每次改动都经过维护者判断，接口和内部结构就不会随着自动生成的代码一起无边界膨胀。TensorCircuit 可以继续增加功能，同时保持严谨、统一和可控。

对于有多年历史和大量用户的项目，这种维护方式基本上是必须的。项目里积累了许多没有完整写进文档的知识：接口为什么这样命名，某个看起来多余的分支在兼容什么，哪些写法属于维护者的个人偏好，哪些内部约定不能轻易改变。这些内容散落在代码、issue、旧版本行为和维护者的经验里。AI 可以读到其中一部分，却很难一次掌握全部背景。

如果直接在这样的项目上激情 Vibe Coding，同时放松人工控制，接口和内部结构很快会失去方向。局部改动各自看起来合理，合在一起却可能互相冲突；旧的隐性约定逐渐被覆盖，新的约定又没有稳定下来，最后整个项目会变得难以预测。

所以实验从一个新项目开始。新项目没有需要继承的历史包袱，公共接口、内部边界、测试方法和 Agent 协作流程都可以从第一天一起设计。TenCirPauli 可以直接围绕 Spec、清晰的语言边界、独立参考和性能测试建立。

## 成熟库给新项目提供坐标

从空白目录开始写库，和对照成熟库构建新库，工作性质差别很大。我参考 QuSpin、OpenFermion、TensorCircuit 和 PauliPropagation.jl，主要看三件事：它们积累的接口经验，长期形成的正确性参照，以及可以实际测量的性能基线。

接口经验来自真实使用。用户怎样组织数据、怎样发起计算、怎样处理大规模输入、怎样连接其他系统，这些问题在成熟库里已经被反复验证。新库早期很容易觉得自己的接口设计得不错，随着功能和使用场景增加，原本局部合理的选择却可能逐渐冲突，最后不同 API 互相打架。

正确性参照让新实现有了可以反复比较的对象。已有库的结果、物理模型和小规模案例，再配合独立参考，能够覆盖大量难以凭空推导的边界情况。

性能基线则给科学计算提供了尺度。一个程序从 10 秒优化到 1 秒，看起来提升了十倍；如果成熟库在同一问题上只需要 100 毫秒，这个程序仍然慢了一个数量级。没有这把尺子，开发者不知道问题通常应该耗时多久，也不知道当前优化究竟解决了主要瓶颈，还是只改动了一小块不重要的代码。

TenCirPauli 就是在这样的坐标系中磨出来的。QuSpin、OpenFermion、TensorCircuit 和 PauliPropagation.jl 分别提供了不同方向的接口、正确性和性能参照。TenCirPauli 借助这些坐标重新选择数据表示和执行路径，把问题设计成适合 Rust 和 Agent 协作的形式。项目的[性能页面](../performance.md)和[研究案例](../../examples/research/README.md)记录了这些对照结果。

## 实验的工作方式

在 TenCirPauli 中，我没有把每个文件和每处修改都亲自检查一遍，也没有用人工阅读保证所有局部实现符合我的审美。人的工作集中在目标、Spec、关键方案和验收标准上。

项目的实现规模已经远超演示项目。截至目前，TenCirPauli 已经超过六万行源代码，Python 和 Rust 大致各占一半。这个规模足以让接口、模块边界、性能和维护性问题真正暴露出来，也足以检验这套开发方式能不能持续运转。

流程大致是：

```text
高能力 AI：整理目标并编写 Spec
        ↓
人：决定关键接口、语义和架构权衡
        ↓
中等能力 AI：根据 Spec 执行实现
        ↓
高能力 AI：审阅实现并生成 Review Report
        ↓
中等能力 AI：根据 Review Report 修复
        ↓
自动化测试、差分验证、Benchmark 和回归检查
        ↓
继续迭代
```

高能力模型负责理解问题、提出方案和审阅复杂实现，中等能力模型负责执行代码工作和修复，人负责做不可逆的设计取舍，自动化系统负责提供持续证据。

## Spec 初稿是最需要高强度讨论的阶段

Spec 要超过功能清单，写清楚用户合同和内部边界：调用方式、概念命名、返回值、数据生命周期、错误类型、失败时机、不同语言层的分工、性能和资源要求，以及独立参考和性能测试的验收方式。

Spec 初稿的讨论，是整套流程里最需要人和机器高强度合作的阶段。高能力 AI 可以列出几种接口方案，比较已有库的做法，分析复杂度、资源消耗、语言边界和未来扩展；人则不断追问用户真正需要什么，哪些抽象会泄露实现，哪些性能取舍值得接受，哪些设计会在规模扩大后互相冲突。这个过程往往要反复几轮，直到接口和主要实现路线都能经得住追问。

TenCirPauli 里最费人的事情通常在于决定一个计算应该归属于哪个抽象：数据应该在哪里保存，什么时候转换，哪些结果应该直接交给用户，哪些工作应该留在底层，哪些通用接口值得保留，哪些地方应该使用专用实现。这些决定会一起影响公共 API、性能、内存、语言边界、错误处理和未来扩展。

后面的代码实现，更多是把已经做出的决定落实下来。真正消耗设计精力的地方，在于初稿阶段把问题问透，把备选方案的代价摊开，把公共 API 和内部数据模型一起定下来。Spec 写错之后，后面的实现可以非常完整，也可以非常一致地错下去。

## 一个面向 Agent 的库

TenCirPauli 也可以由人直接使用。它有 Python API、文档、示例和 TensorCircuit-NG 集成，公共接口需要保持自然。从设计目标看，它同时面向代码 Agent。

Agent 需要从名称、类型和文档里推断能力边界，处理显式错误，得到确定性输出，并通过一次完整调用完成工作。不同步骤之间的数据传递也应该尽量直接，减少无意义的转换。能力名称要清楚，结果合同要稳定，数据生命周期要容易理解，内部顺序不能影响公开结果，专用路径要有明确的能力边界。

这会改变一些传统的抽象取舍。为了性能和执行确定性，内部实现可以牺牲一部分通用性，保留面向特定数据结构的路径。公共接口保持清楚，底层实现则可以更加专用。

## 测试、Benchmark 和全局巡检

没有逐行人工审查，测试和 Benchmark 就是开发流程的核心部分。它们需要持续回答四个问题：

- 结果是否正确。不同规模、边界情况和代表性工作负载都要和独立参考比较。
- 公共合同是否正确。参数、返回值、错误类型、失败时机和确定性行为都需要测试。
- 性能测试是否测到目标路径。测试要覆盖真实的用户调用，区分准备成本和重复执行，避免测试名称和实际行为不一致。
- 修改是否造成回退。性能改动要有前后对照，语义改动要有独立数值测试，删除旧路径之后要检查相关功能的覆盖情况。

单轮 AI Review 主要看当前改动，覆盖不了整个仓库里逐渐积累的问题。项目还需要定期做全局 AI 巡检，每次围绕一组明确的问题重新扫描代码、文档、测试和性能记录。巡检可以寻找隐藏的 bug 和边界错误，定位真正的性能瓶颈，核对实现与对外 claim 是否一致，清理 dead code 和重复实现，也可以检查接口之间是否又出现了新的冲突。

单轮 Review 处理眼前的变化，全局巡检处理项目的长期熵。巡检报告交给后续的实现模型修复，再用自动化检查确认结果。两种节奏结合起来，项目才不会只在新增功能时变得越来越复杂。

## AI 会犯什么错？

答案是：会。仓库里仍然可能留下隐藏的性能不足、很难察觉的细微 bug，以及重复堆叠的无用代码。这些问题很难彻底抓干净，人审过的代码里同样会有。

工程上更重要的判断，是最关注的用户案例和可用路径有没有足够强的测试与性能基线。只要这些路径上的正确性和性能得到持续保证，项目就已经具备实际使用的基础。看起来像鸭子，叫起来像鸭子，那它就是鸭子。使用者首先关心它是否给出正确结果、是否在合理时间内完成任务、是否能稳定地接入工作流。

## 可维护性也由 Agent 参与

过去，人们经常质疑一个项目：“功能虽然能用，里面却是屎山代码，后面肯定维护不了。”这个担忧来自一个默认前提：未来的维护者主要是人，人需要读懂代码、定位问题、修改实现，再重新验证结果。

现在这个前提发生了变化。TenCirPauli 的后续维护也可以由 Agent 完成。只要项目有清楚的 Spec、足够的测试、性能记录和巡检报告，Agent 就能在明确指令下定位问题、提出修改、执行验证。Agent 还能持续完成维护，项目的可维护性就仍然处于可控范围。

这引出了一种新的实现不可知论：不预先要求内部代码必须符合某一种人类审美，也不把“有人觉得代码难看”直接等同于“项目不可维护”。先看用户合同是否成立，再看性能和正确性证据是否稳定，最后看 Agent 能不能持续修改和验证。对 Agent-facing 软件来说，这是一套新的维护标准。

## 结语

TenCirPauli 是一次 Rust 量子软件尝试，也是一场 AI 编程实验。

我想验证的是：把人的精力从逐行审阅代码转移到问题定义、接口设计、架构权衡、测试系统和性能证据上，能不能得到一个严谨、可复现、可维护的科研软件库。

到目前为止，答案是可以，但工程工作转移到了更高层：Spec、架构、测试和性能证据。

AI 能扩大实现带宽，不能自动产生正确抽象。真正需要人做的，是定义问题、冻结合同、决定关键取舍。Agent 负责实现、审阅和修复，自动化系统持续提供证据。对于科研软件，这是一种可以扩大开发规模的新工作方式。
